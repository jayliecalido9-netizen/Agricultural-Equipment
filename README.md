# Agricultural Equipment and Asset Management System

A system developed to manage agricultural machinery, equipment, and other municipal agricultural assets. It supports equipment reservations, borrowing and return transactions, maintenance scheduling, equipment availability monitoring, and asset utilization tracking to improve operational efficiency.

AEAMS serves the Bongabong Municipal Agriculture Office and owns the `aeams` schema in a centralized PostgreSQL database.

The application includes React/TypeScript/Vite, Express/TypeScript, Prisma/PostgreSQL, JWT login, role permissions, equipment/photos, reservations, borrowing/release, inspected returns, maintenance, availability calendars, utilization, CSV/PDF reports, notifications, users, settings, audit history and integration configuration.

## Run on Windows

For HTTPS hosting with private database/API ports, separate production secrets, and complete database/photo backups, use the [production deployment guide](docs/production.md).

Start Docker Desktop with its Linux engine, then open PowerShell:

```powershell
Set-Location 'C:\Users\jayma\OneDrive\Desktop\Agricultural Equipment and Asset Management System'
.\scripts\Start-Application.ps1 -Demo
```

This creates missing configuration, builds services, deploys migrations, initializes permissions and installs **fictional demonstration data**. Existing `.env` credentials and demo fixtures are preserved. The migration service exits successfully after setup; that is normal.

**This workspace uses http://localhost:3002** because existing containers occupy ports 3000 and 3001. New configurations default to port 3000. `FRONTEND_PORT` and `FRONTEND_ORIGIN` in `.env` must agree; the startup script prints your URL.

## Development logins

All demonstration accounts use **`DEMO_ADMIN_PASSWORD` from your local `.env`**. It is generated by default and can be replaced with a locally configured development password. Open `.env` locally; never commit or share it.

`POSTGRES_ADMIN_PASSWORD`, `AEAMS_MIGRATOR_PASSWORD`, and `AEAMS_APP_PASSWORD` are internal database credentials, not website login passwords. Keep them consistent with PostgreSQL and the connection URLs. Changing them in `.env` does not update existing database accounts.

| Role | Email |
| --- | --- |
| Admin | `admin@example.test` or configured `DEMO_ADMIN_EMAIL` |
| Employee | `employee@example.test` |

All demo identities, references, locations, equipment and transactions are fictional. There are two active demo accounts: Admin and Employee. Farmers remain external borrower references. Older demo identities are inactive and retained for transaction history. Rerunning the seed does not reset existing passwords. Administrators can reset other accounts in Users & Roles.

For an empty installation, omit `-Demo` and create the first administrator using [deployment instructions](docs/deployment.md).

## Workflows

1. **Equipment:** Inventory → Add equipment → enter the asset, category, location and condition. Photos are optional. Edit/archive from the detail page; create categories/locations through the associated dialogs.
2. **Reservations:** Request a future window with a current farmer verification. Admin approves/rejects; committed windows appear on the calendar. Transfer an approved reservation to a linked borrowing request.
3. **Borrowing:** Request → administrator approves → Employee inspects and releases within the borrowing window. Open printable PDF receipts from the transaction row.
4. **Returns:** Record actual return, inspected condition, damage/missing accessories and optional usage. The inspection and return commit together. Damage keeps the asset unavailable and creates a damage report/maintenance alert.
5. **Maintenance:** Schedule and assign work → Start → Complete with cost, repair notes and assessed condition. Recurring plans track due dates; work orders reserve actual downtime.
6. **Reports:** Select a report/date/category/status → review, print, export CSV/PDF. Utilization separates elapsed borrowing time from logged operating hours and supports monthly/annual date windows.

PostgreSQL enforces booking conflicts across reservations, borrowing and maintenance. **An active loan or work in progress blocks future use until returned/completed.** This conservative policy can prevent release when an unbounded active window conflicts with a future commitment. Resolve/reschedule commitments first. [Database rules](docs/database.md).

The UI labels Requested as Pending, Released as Borrowed, and Fulfilled as Completed. Borrowing rejections are stored as Cancelled with a `Rejected:` reason. The API uses canonical database status values.

## Host development

Requirements: Node.js 22.12+ and PostgreSQL. Use the exact `FRONTEND_ORIGIN` URL when signing in.

```powershell
docker compose up -d --wait db
npm ci
npm run db:generate
npm run db:migrate
npm run db:bootstrap

# Optional fictional demo fixtures:
$env:ALLOW_DEMO_SEED = 'true'
npm run db:seed
Remove-Item Env:ALLOW_DEMO_SEED

# Terminal 1:
npm run dev:backend

# Terminal 2:
npm run dev:frontend
```

Do not run host API/frontend processes and their containers on the same ports. Vite may choose a later free port; update `FRONTEND_ORIGIN` and restart the API if the origin changes. In this workspace, use `http://localhost:3002`. To compile both applications, run `npm run build`; `npm start` runs the compiled API.

## Verification

```powershell
npm run db:validate
npm run typecheck
npm test
npm run test:api
npm run test:postgres:local

# With the app running and demo accounts installed; requires Microsoft Edge:
$env:BROWSER_BASE_URL = 'http://localhost:3002'
npm run test:browser
Remove-Item Env:BROWSER_BASE_URL
```

The embedded PostgreSQL suite runs 34 constraint/seed/permission/migration tests. API tests use an isolated PostgreSQL database with the restricted runtime login. The concurrency test races independent approvals. Tests remove only their own generated `aeams_test_*` databases. Browser checks create an explicitly fictional QA asset, edit it, approve/cancel its reservation, approve/release/return a borrowing and archive it; immutable QA history remains. Screenshots are ignored under `test-results/`. [Verification record](docs/testing.md).

## Operations

```powershell
docker compose ps

docker compose restart backend frontend
.\scripts\Backup-Database.ps1

# Preserve data and photos:
docker compose down
docker compose up -d --wait
```

Never add `--volumes` when retaining records. PostgreSQL and photos use named volumes. Changing `.env` passwords after initialization does not rotate database roles. A database dump does not include uploaded photos; back up `equipment_uploads` separately. [Recovery instructions](docs/deployment.md).

## Integration boundaries

FFRMS owns farmer/farm registration; APMS production; AISMS consumable stock; AASMS assistance approvals; ABPMS official procurement/finance. AEAMS owns durable assets and their transactions, uses stable references, and does not write other modules' tables.

Development connections are **Mock**, not Connected. Live health checks require an explicitly allowed HTTPS host, module-specific backend token and a response identifying that module. Verification expires after five minutes. Utilization events are stored atomically in an outbox, but **automatic outbound delivery and live farmer synchronization remain disabled until remote contracts are agreed**. [Integration guide](docs/integration-guide.md).
